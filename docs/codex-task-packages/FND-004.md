## 6. Schema Ownership Model

**Settled facts, inherited from the Codex Spec, not re-opened by this task** (`docs/codex-spec-revb1.docx.md:105-108`):

* Runtime database connection uses a **single, non-superuser `app_rw_user`** for Phase 1 — module-scoped connection pools are explicitly rejected for now ("Phase 1 採單一非 superuser app_rw_user；不採 module-scoped DB pools").
* Write-isolation enforcement is **primarily** repository-ownership convention + a static SQL scanner (FND-006's future scope) + the `owning_context` migration header + human review — **not** primarily runtime DB-role enforcement.
* Per-context DB role grants are explicitly retained **only as a migration-level proof**, not a claim of full runtime enforcement ("保留 per-context DB role grant 作為 migration-level proof，不宣稱 runtime 全面 enforce").
* `app_rw_user` must not be the database owner or a superuser; only a distinct, non-runtime migration role may execute dangerous DDL.

**Settled by Human Review (Gate A amendment):**

### Schema owner

* Every one of the twelve schemas is created and owned by **whichever role executes the migration** — this document does not hard-code, invent, or propose a specific migration-role name anywhere, including in any future SQL.
* **FND-004 does not create or provision any database role of any kind.** Role creation and credential provisioning are environment/deployment concerns, not this task's scope.
* The deployment environment (not this task) must invoke `migrate:up`/`down`/`redo` using an approved, non-runtime migration role — that role must never be the same identity as any application runtime credential.

### Runtime role

* The authoritative Phase 1 runtime role name is **`app_rw_user`** (already fixed by the Codex Spec, §3.1) — its existence is treated as an environment/deployment precondition, not something FND-004 provisions.
* FND-004 **defines** (as a future privilege *contract* to be applied by its one migration, §11/§12) that `app_rw_user`:
  * receives `USAGE` on each of the twelve schemas;
  * receives no `CREATE` on any of the twelve schemas;
  * owns no schema;
  * is not the database owner;
  * is not a superuser.
* **FND-004 does not create `app_rw_user`** — only applies the `GRANT`/`REVOKE` contract above, assuming the role already exists as an environment precondition.

### Proof roles

* **FND-004 does not create twelve (or any number of) production `<context>_role` roles.** This question is resolved as **no** — removed from open questions.
* Any per-context or unauthorized-role privilege probe (the "wallet role cannot write reward.\*" proof the Codex Spec requires, `docs/codex-spec-revb1.docx.md:107`) must use **ephemeral, test-only roles created inside the isolated Gate F PostgreSQL environment and removed during that same gate's cleanup** — following the exact isolation/cleanup discipline FND-003's own Gate F already established (unique container, unique credentials, full teardown).
* These ephemeral test-only roles: are **not** repository artifacts (they appear in no committed file); are **not** production roles; are **not** created by the committed migration; and **do not** establish any future production naming convention. Their names, if any are chosen at Gate F time, are disposable test-harness detail, not a governance decision this document makes.

**Centralized schema ownership, settled**: every schema is owned by the identity that executes the migration (above) — not by twelve distinct owner roles. This does not contradict the Codex Spec's "Owner Module" column, which describes *architectural* module ownership, not literal PostgreSQL schema-owner identity — this distinction (physical DB ownership vs. architectural module ownership) remains explicit precisely because no document otherwise separates the two.

**Who may `CREATE` in each schema**: only the role executing the migration, ever. No runtime role (including `app_rw_user`) holds `CREATE` on any schema; all schema and table DDL flows exclusively through migrations.

**Who may `USAGE` each schema**: `app_rw_user` receives schema-level `USAGE` on all twelve schemas, granted by this task's one migration — and nothing else. Schema-level privileges (`USAGE`, `CREATE`) and object-level privileges (`SELECT`/`INSERT`/`UPDATE`/`DELETE`/`REFERENCES`/`TRIGGER`/sequence/function-execution grants) are **distinct PostgreSQL privilege layers**; FND-004 creates no object of any kind (§16), so it grants no object-level privilege of any kind. Any future `SELECT`/`INSERT`/`UPDATE`/`DELETE` grant on a table, view, or other object inside these schemas is entirely the responsibility of the future domain migration that creates that object, and that future grant must independently satisfy owning-context ownership, the cross-schema write ban (§9), least privilege, approved projection/service contracts, and Human Review — it is never implied, pre-authorized, or made automatic by this task's schema-level `USAGE` grant. No production per-context role is created to demonstrate narrower scoping — that proof is Gate F's ephemeral-role responsibility, above.

No production credential, password, connection string, or invented migration-role name is present anywhere in this document.

## 7. Public Schema Posture

**Settled by Human Review (Gate A amendment): Posture A, adopted precisely.**

* Revoke `CREATE` on schema `public` from `PUBLIC` (the PostgreSQL pseudo-role, not this repository's `public` schema — the standard, default-installed grant every new PostgreSQL database ships with).
* Retain ordinary `USAGE` required by PostgreSQL/`node-pg-migrate` itself (which needs to create/read `public.pgmigrations`).
* `public.pgmigrations` stays in place — **moving it is explicitly out of FND-004 scope**.
* No application/domain object may be introduced into `public` by FND-004.
* **FND-004 installs no PostgreSQL extension.**
* **FND-004 does not move, alter, or delete any pre-existing extension-owned object.**
* Future extension placement requires separate governance (§13).
* Future application extensions should prefer an explicitly governed dedicated schema rather than `public`.

Justification: the Codex Spec's own cross-context read-contract pattern (`docs/codex-spec-revb1.docx.md:84-97`, "Public Read Contract" column) routes all cross-context reads through dedicated `<context>_public.*` schemas (e.g. `wallet_public.wallet_summary`), **not** through the PostgreSQL built-in `public` schema — meaning `public` was never intended to hold any business/domain object at all under this architecture. Posture B (revoke both `CREATE` and application `USAGE`) is not adopted because `node-pg-migrate` itself requires ordinary `USAGE`/read/write access to `public.pgmigrations` to function, and revoking that would break the already-approved migration framework.

* **Is `public` application-object-free?** `public.pgmigrations` (framework infrastructure, not a business object) is the only object FND-004 itself introduces into `public`. **This document does not claim `public.pgmigrations` is guaranteed to be the only pre-existing object in every deployment** — a given environment may have other pre-existing, non-repository-created objects in `public` (e.g. from an extension or prior manual action) that FND-004 neither creates nor is responsible for. For clean Gate F verification purposes, `public.pgmigrations` may be treated as the only *expected* repository-created object.
* **May extensions use `public`?** Deferred, not blocking — see §5.6/§13.
* **Does `public.pgmigrations` remain in `public`?** Yes — **moving it is explicitly out of scope**. FND-003's shipped, currently-enforced wrapper design hardcodes `--schema public --migrations-table pgmigrations` in `up.mjs`/`down.mjs`/`redo.mjs`'s fixed argument arrays (§4). Moving it would require modifying `scripts/migrate/**`, which this task's own forbidden scope (§16) does not authorize.
* **Is moving `pgmigrations` in scope?** No. Settled as explicitly out of scope for this task.

## 8. Search Path Policy

**No repository document specifies PostgreSQL `search_path` handling for schema isolation** — a genuine, confirmed gap (zero hits for `search_path` anywhere in the repository). **Settled by Human Review (Gate A amendment)**, replacing this document's original proposal that FND-004 directly alter `app_rw_user`'s `search_path`:

* **Every FND-004 DDL statement and every object reference must be explicitly schema-qualified.** No migration behavior may depend on implicit application-object resolution.
* **FND-004 does not execute `ALTER ROLE ... SET search_path`**, for `app_rw_user` or any other role.
* **Runtime `search_path` hardening is a deployment/role-provisioning contract, deferred to the task that owns role provisioning** — not decided or implemented by FND-004.
* Application SQL must continue to use explicit schema qualification, as a standing architectural requirement independent of this task.
* User-controlled `search_path` is forbidden, as a standing architectural requirement.
* `public` must not become an application-object lookup namespace.
* **The migration session may retain its environment-provided `search_path`, because the migration itself must not rely on it** — every statement the migration issues is schema-qualified by construction (`CREATE SCHEMA <name>;`, fully-qualified `GRANT`/`REVOKE` targets), so whatever `search_path` the migration role's session happens to have is architecturally irrelevant to correctness.
* **FND-004 does not invent or enforce a role-level `search_path` value.** This removes the prior proposal to set `app_rw_user`'s `search_path` to `public` only — that decision now belongs entirely to whichever future task owns role provisioning.

## 9. Cross-Schema Dependency Policy

**Settled, hard rule, inherited unconditionally** (`CLAUDE.md:11`, `docs/codex-spec-revb1.docx.md:107,138`, `docs/tds-revb-final.md:1113`): cross-schema `INSERT`/`UPDATE`/`DELETE` is forbidden for every schema except `platform.event_outbox`. This task does not relax, qualify, or re-interpret this rule.

Since FND-004 creates only *empty* schemas (no tables exist yet in any of the twelve), this section defines **policy for future tasks**, not a behavior FND-004 itself exercises. **Settled by Human Review (Gate A amendment) — approved and marked settled, not merely proposed:**

* **Cross-schema `INSERT`/`UPDATE`/`DELETE` is forbidden.** The only existing exception is `platform.event_outbox`.
* **Direct cross-context reads from source-of-truth tables are forbidden without an explicit, time-limited Tech Lead waiver.**
* **Cross-schema foreign keys are forbidden.**
* **Cross-schema views over source-of-truth tables are forbidden.**
* **Transactions containing writes to more than one owning context are forbidden**, except the approved event-outbox pattern.
* **PostgreSQL physical capability does not create architectural permission** — FKs/joins are technically possible in PostgreSQL but remain architecturally forbidden by the rules above, enforceable in the future via FND-006's static SQL scanner and repository-ownership review, not by a PostgreSQL-level technical restriction alone.
* **Read sharing must use a future governed projection/service contract** — not created by this task.
* **FND-004 creates no `<context>_public` schema, view, or projection** (§5).

**The required waiver process must include:**

* named owner;
* reason;
* affected contexts;
* expiry date;
* removal plan;
* Human Review/Tech Lead approval.

This mirrors and formalizes the pattern already implied by `docs/tds-revb-final.md:173` (Tech Lead waiver + expiry + projection backlog); "permanent ad-hoc cross-schema join" remains explicitly forbidden as an outcome under any waiver.

**Separated explicitly, per this section's own requirement:**
* **Physical PostgreSQL capability**: cross-schema FKs, views, and joins are all physically possible in PostgreSQL and are not restricted by anything FND-004 creates at the schema level alone.
* **Architectural permission**: forbidden by default (above), enforceable in the future only via FND-006's static SQL scanner and repository-ownership review — not by a PostgreSQL-level technical restriction, since GRANT/REVOKE alone cannot prevent same-role FK/join syntax from being technically valid.
* **Application-layer ownership**: each schema's business objects are owned, in the architectural sense, by exactly one bounded context/module, per the Codex Spec's Owner Module column — enforced by code review, CI fitness functions (future FND-006), and this task's own role/grant scaffolding (§6), not by application code itself.

## 10. Owning Context Contract

FND-003's header grammar is unchanged by this task (§4): exactly one `owning_context` value per migration file, from the fixed 12-value allowlist, duplicate field rejected as `MIG009_DUPLICATE_HEADER_FIELD`. **This grammar is not changed by this task, and multiple `owning_context` headers remain forbidden.**

**Settled by Human Review (Gate A amendment):**

* **The single future migration uses `-- owning_context: platform`.**
* **Rationale**: this is a platform-level infrastructure migration; the metadata identifies *responsibility for the migration artifact*, not business-data ownership. Tagging the migration `platform` **does not transfer** business-data ownership from the twelve bounded contexts to `platform` — each schema's eventual data still belongs, architecturally, to its own bounded context (per the Codex Spec's Owner Module column); `platform` here identifies only who is responsible for the infrastructure act of creating the schema.
* **FND-003 permits exactly one `owning_context` value per file** — this is a hard, structural constraint (not a policy choice) that independently confirms `platform` (not a per-schema value) is the only workable tag for one migration creating all twelve schemas.
* **Schema-creation migrations require special rollback/forward-fix notes**: `rollback_notes` must state that the schema(s) may be safely dropped only if provably empty, and `forward_fix_notes` must state that once any downstream task has created a real object inside a given schema, that schema may never be dropped by a rollback again, only forward-fixed (§13's rollback threshold).

## 11. Migration Design Options

Two designs were compared during Gate A research; **Human Review has since settled this question in favor of exactly one migration** (§12). The comparison is preserved below for transparency, not because either option remains open.

### Design A — one migration (settled choice, see §12)

A single SQL migration, tagged `owning_context: platform`, issues all twelve `CREATE SCHEMA` statements plus the `public`-hardening `REVOKE`/`GRANT` statements (§7) plus the minimal approved schema-level privilege contract (§6), in one file, one transaction (`--single-transaction`, inherited from FND-003).

* **Atomicity**: highest — either all twelve schemas and all grants exist, or none do (rolled back together).
* **Rollback clarity**: highest — one `down` migration reverses everything in one step, as long as all twelve schemas remain empty (§13).
* **Partial-failure risk**: lowest — `--single-transaction` means a failure on schema #7 rolls back schemas #1-6 too, leaving a clean, fully-absent state, never a half-created one.
* **Reviewability**: a single file is easy to review for this bootstrapping use case (twelve near-identical `CREATE SCHEMA` statements plus grants).
* **Future ownership changes**: a future task wanting to change just one schema's grants needs a **new** migration (forward-fix), not a modification of this one — consistent with FND-003's immutability policy.
* **`node-pg-migrate` ordering**: irrelevant for a single file — no inter-file ordering question arises.
* **FND-003 validation compatibility**: fully compatible — one filename, one header, one `owning_context` value (structurally required anyway, per §10).

### Design B — separated migrations (considered, not selected)

## 13. Rollback and Forward-Fix Policy

**Settled by Human Review (Gate A amendment):**

* **`DROP SCHEMA ... CASCADE` is never used**, in any rollback or forward-fix, for any reason. `CASCADE` silently destroys dependent objects and is incompatible with this repository's "never silently destroy data" posture.
* **`down` may drop only schemas created by this migration that remain empty.** Before Gate D/F verification ever runs a real `down`, the migration's own rollback logic (or, more practically, its documented `rollback_notes`) must state this precondition explicitly; a schema containing even one object created by a *later* task's migration must never be dropped by this task's rollback.
* **`down` must fail safely if any schema contains a downstream object** — rollback is prohibited from that point forward; a forward-fix migration is the only permitted correction path.
* **Rollback threshold, stated explicitly**: once any downstream migration creates an object in any FND-004 schema (FND-005's `platform.event_outbox`, or any domain task's first table), destructive FND-004 rollback is **permanently prohibited**. This mirrors FND-003's own already-established policy: "once a migration has reached a shared environment, do not edit or reverse it — write a new forward migration."
* **Thereafter, correction is forward-fix only.**
* **Privilege corrections after merge are forward-fix migrations, not edits to the original migration** — any correction to schema ownership, grants, or the schema set itself is a new, separately-authored migration, never an edit to this task's original file.

No deviation from this posture is proposed. Any future deviation requires explicit Human Review.

## 14. Security and Least-Privilege Requirements

* `app_rw_user` (inherited, settled): never the database owner, never a superuser.

* No search_path shadowing: FND-004 relies on universal schema-qualification (§8), not a role-level `search_path` restriction it does not set, and never grants any runtime role `CREATE` on any schema.
* Least privilege: `app_rw_user` receives schema-level `USAGE` on all twelve schemas (since it is the single Phase-1 runtime identity for every context) but no schema-level `CREATE` anywhere and no schema ownership. **This task grants no object-level privilege of any kind** — no `SELECT`/`INSERT`/`UPDATE`/`DELETE`/`REFERENCES`/`TRIGGER`/sequence/function-execution grant — because it creates no object of any kind (§16); schema-level and object-level privileges are distinct PostgreSQL privilege layers, and every future object-level grant belongs to the future domain migration that creates that object.
