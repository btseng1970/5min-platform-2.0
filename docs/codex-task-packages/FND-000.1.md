# FND-000.1｜Node.js LTS version alignment (patch to FND-000)

Locally-introduced patch task, not part of the original Codex Spec v1.0 RevB.1 task list. Naming mirrors the ADR-000.x convention (§2.1) applied to a task package: a small, independently reviewable follow-up to an already-closed task (FND-000), rather than new scope folded into FND-001. Full 16-field package supplied for consistency with FND-012's docs lint requirement, condensed where the patch is genuinely small.

## 1. Task ID
FND-000.1

## 2. Objective
Align every Node.js version reference created by FND-000 (`.devcontainer/Dockerfile`, `.github/workflows/ci.yml`) with the Node **24** LTS decision made during FND-001 planning, so the devcontainer/CI Node version is single-sourced from the same `.nvmrc` that FND-001 introduces at the repo root, and reflects a support horizon that covers this platform's Japan market timeline through Phase 3. This package does **not** touch `apps/**`, `packages/**`, or any FND-001 workspace file — those stay FND-001's own concern.

## 3. Source of Truth
`docs/adr/ADR-000.md`（Node.js LTS 決策，未釘定確切版本）＋ `docs/adr/ADR-000.1.md`（**Accepted，commit 686a925** — 第 1 項 Runtime：Node.js 24 LTS、支援範圍 `>=24 <25`、Node 25 EOL/不支援、`.nvmrc` 內容為 `24`，為本任務版本裁決之權威來源）＋ 本文件第 10 項記錄之額外時程理由（2026-07-14，Node 22 維護期早於日本市場時程 vs. Node 24 覆蓋 Phase 3）＋ FND-001 引入之 root `.nvmrc`（作為版本唯一真相來源，本任務讀取但不擁有）。

## 10. Node 24 LTS 選定理由（依你的裁決逐字保留）

Node 22 維護期（Maintenance LTS）於 2027 年中屆滿，早於本平台日本市場時程；Node 24 LTS 支援至 2028 年中，覆蓋全 Phase 3。因此選定 Node 24 LTS 作為全環境統一版本，取代 FND-000 原先暫定的 Node 22。

## 11. Implementation Steps
1. `.devcontainer/Dockerfile`：`FROM node:22-bookworm` → `FROM node:24-bookworm`。
2. `.github/workflows/ci.yml`：`actions/setup-node@v4` 的 `with:` 區塊由 `node-version: 22` 改為 `node-version-file: '.nvmrc'`，讀取 FND-001 建立的 root `.nvmrc`（內容為 `24`）。**排序相依性**：本步驟要求 FND-001 的 root `.nvmrc` 已存在於 repo 中，否則 CI 會因找不到檔案而失敗；因此 FND-000.1 的此項變更必須與 FND-001 的 `.nvmrc` 同時或在其之後 commit，不得單獨先行。
3. `scripts/dev/package.json`：新增 `"engines": { "node": "24.x" }`。
4. `scripts/dev/.npmrc`（新增檔案）：內容精確符合：唯一一行設定為 `engine-strict=true`；允許標準結尾換行；不得有其他設定、註解或空行。**修正（Option A）**：`scripts/dev` 擁有自己的 `package.json`/`package-lock.json`，非 root npm workspace 成員（ADR-000.1 §3）；npm 的 per-project `.npmrc` 解析以 cwd/專案邊界為準，**不會**沿目錄樹向上查找並套用 root 的 `.npmrc`。因此 `scripts/dev` 的 `engine-strict` 強制執行**必須**由其自身的 `.npmrc` 明確提供，不得假設或依賴 root `.npmrc` 的繼承（先前版本本任務文件中「向上層目錄查找時對 scripts/dev/ 內的指令同樣生效」之敘述有誤，已於本次修訂移除）。

## 12. Acceptance Criteria
* `.devcontainer/Dockerfile` base image 為 `node:24-bookworm`。
* `.github/workflows/ci.yml` 之 `actions/setup-node@v4` 使用 `node-version-file: '.nvmrc'`，CI log 確認實際使用的 Node 版本為 24.x。
* `scripts/dev/package.json` 宣告 `"engines": { "node": "24.x" }`。
* `scripts/dev/.npmrc` 存在，且其內容精確符合以下定義：唯一一行設定為 `engine-strict=true`；允許標準結尾換行；不得有其他設定、註解或空行。
* **負向路徑驗證（修訂，Option A）**：
  * **Root workspace**：搭配 root `.npmrc`（`engine-strict=true`，FND-001 建立）後，於 Node 24 下 `npm ci` 須以 exit code `0` 成功；於 Node 22 下**相同的** `npm ci` 須因 Node engines 不符而失敗（`EBADENGINE`/unsupported engine 訊息）。
  * **`scripts/dev`**：搭配 `scripts/dev` **自身**的 `.npmrc`（本任務新增，`engine-strict=true`）後，於 Node 24 下 `npm ci` 須以 exit code `0` 成功；於 Node 22 下**相同的** `npm ci` 須因 Node engines 不符而失敗，理由同上。**不得**假設或依賴 root `.npmrc` 對 `scripts/dev` 產生任何強制效果。
  * 兩個情境皆須以**相同 npm 版本（11.9.0）**、僅 Node major 版本不同（22 vs 24）進行對照，確保 Node 版本是唯一刻意變動的變因。
  * 驗證方法見 §13，使用官方 `node:22-bookworm`／`node:24-bookworm` **base image** 啟動之**一次性、拋棄式 container**（不建置、不 commit、不 publish derivative image；container 執行個體本身不得被 commit 或重複使用）。**不得**透過 `nvm`/host runtime 切換本機 Node 版本，亦**不得**修改 `.nvmrc`。
* `apps/**`、`packages/**`、`migrations/**` 未被觸碰。

## 13. Tests Required
* CI 本身即為測試：確認 Node 24 runner 下 `postgres:16` service 仍正常啟動，FND-000 既有的 `smoke-test.mjs`、`partition-test.mjs` 仍全部通過（迴歸測試：升級 Node 版本未破壞既有環境檢查）。
* 本機：`docker compose build app` 在更新後的 Dockerfile 下成功建置（devcontainer image 於 Node 24 下可正常建置）。
* **負向路徑驗證方法（修訂，Option A：scripts/dev 使用自身 .npmrc，不依賴 root 繼承）**：
  * 使用官方 `node:22-bookworm` 與 `node:24-bookworm` **base image**，不建置、不 commit、不 publish 任何 derivative image；容器內 npm 得標準化為 `11.9.0`，但僅限於**拋棄式 container 檔案系統內部**，該 container 執行個體本身不得被 commit 或重複使用（"Use official node:22-bookworm and node:24-bookworm base images without building, committing, or publishing a derivative image. npm may be normalized to 11.9.0 only inside the disposable container filesystem. The container must not be committed or reused."）。**不透過 `nvm` 安裝或切換 host Node 版本，不修改 `.nvmrc`**。
  * **npm 版本一致性（container toolchain 準備，非受測指令本身）**：container 啟動後，先以該 image 內建 npm 執行 `npm install -g npm@11.9.0`，將 container 內 npm 統一升級／降級至 `11.9.0`。此步驟僅屬 container toolchain 準備，**不構成**受測的正向/負向驗證指令本身——受測指令一律為 `npm ci`（見下）。
  * 驗證範圍為兩個獨立情境，**皆須執行**，且**不得互相依賴或繼承對方的 `.npmrc`**：
    (a) **root workspace**：複製 root `package.json`、root `package-lock.json`、root `.npmrc`，以及所有 workspace 成員的 `package.json`（僅 manifest，不含 `src/`、不含既有 `node_modules`）。
    (b) **`scripts/dev`**：複製 `scripts/dev/package.json`、`scripts/dev/package-lock.json`、`scripts/dev/.npmrc`（本任務新增檔案）。**不得**額外複製或引用 root 的 `.npmrc`。
  * repo 以**唯讀**掛載；所需 manifest/lockfile **複製**（非可寫 bind mount）到 container 內一個**拋棄式目錄**，僅保留驗證所需最小檔案子集；受測指令僅作用於該複本，**不產生**任何寫回 host repo 的 `node_modules`、lockfile 變更、cache 或其他產出物；container 以 `--rm` 啟動，結束自動移除。
  * **受測指令統一為 `npm ci`**（不使用模糊的「`npm install`/`npm ci`」措辭），四個情境如下，**皆須執行**：
    * Root workspace／Node 24：`npm ci` 必須以 exit code `0` 成功。
    * Root workspace／Node 22：**相同的** `npm ci` 必須因 engines 不符而失敗。
    * `scripts/dev`／Node 24：`npm ci` 必須以 exit code `0` 成功。
    * `scripts/dev`／Node 22：**相同的** `npm ci` 必須因 engines 不符而失敗。
  * **安裝前檢查（每個情境、每個 Node 版本皆執行並記錄）**：於執行 `npm ci` 之前，於 container 內依序執行：
    * `node -v`（預期：情境對應之 22.x 或 24.x）
    * `npm -v`（預期：`11.9.0`，兩種 Node 版本皆同）
    * `npm config get engine-strict`（於拋棄式複本目錄內執行；預期：`true`）
  * 失敗情境（Node 22）之輸出須可明確歸因於 Node engines 不符（`EBADENGINE`/`Unsupported engine`）；擷取該段輸出作為證據。
  * **明確禁止**：不得使用 `--force`、`--ignore-engines`，或任何停用 `engine-strict` 的手段。
  * **image 可稽核性**：驗證報告須記錄每個所用官方 base image 之 resolved image ID/digest（例如 `docker image inspect --format '{{.Id}}'` 之輸出）。
  * 驗證完畢後，於 host 重新確認 `node -v` = `v24.18.0`、`npm -v` = `11.9.0` 未受影響（container 隔離下不預期變動，此步驟為確認性質）。
  * **執行前置程序**：實際執行本驗證前，須先向 Human Review 展示：(i) 確切 docker 指令、(ii) 驗證範圍說明（root workspace / scripts/dev，兩者分別使用各自 `.npmrc`）、(iii) 拋棄式複本如何防止 repo 變更之說明，並取得**獨立於本任務 package 本身核准之外**的執行核准，方可實際 `docker pull`/執行 container。
