## 2. Objective

Establish the SQL-first database migration framework that all subsequent Foundation and domain tasks (FND-004 Schema isolation, FND-005 Event outbox base, and later domain-schema work) will use to add real DDL. This task creates **only the framework**: directory/naming conventions, an `owning_context` header convention, a migration template, a forward-migration + rollback/forward-fix documentation policy, a validation tool that enforces those conventions deterministically, and local developer commands under `scripts/migrate/**`. This task does **not** create any application, platform, or domain schema, table, or column; it does not create `platform.event_outbox` (FND-005) or any `campaign`/`wallet`/`qr`/`reward`/`notification`/`compliance`/`crm`/`team`/`ip_asset`/`analytics`/`commerce` schema (FND-004). **CI wiring ownership is a settled decision, not open scope**: FND-003 establishes the local migration framework and validation command; FND-006 owns all CI integration. This task must not modify `.github/workflows/ci.yml` under any circumstance.

## 6. Allowed Files

Proposed **minimally, based on documentary evidence** (§15 digest row `docs/codex-spec-revb1.docx.md:304`: "Allowed: migrations/README, template, scripts/migrate/**"):

**Allowed (unconditional):**

* `migrations/README.md` — conventions document: directory layout, naming, `owning_context` header format, forward-fix policy, rollback documentation requirement.
* `migrations/template.sql` — exact path, no alternative (see §11.1 correction). Contains no executable DDL (see §12 and Implementation Steps for the exact content constraint).
* `scripts/migrate/**` — validation tooling, local developer commands, **and all migration-validation test harnesses and positive/negative fixtures**. The prior draft proposed a separate top-level test directory outside `scripts/migrate/` for these fixtures; that is withdrawn because the §15 digest row names only `migrations/README`, `migration template`, and `scripts/migrate/**` as Allowed — it does not name any other `tests/`-style path for this task. All fixture and harness content is therefore relocated under `scripts/migrate/**`. Proposed example structure (Gate C design reference only, **not implementation authorization, not created now**):
  * `scripts/migrate/validate.mjs` — validator entrypoint.
  * `scripts/migrate/lib/**` — validator implementation modules.
  * `scripts/migrate/fixtures/valid/**` — positive fixtures (well-formed example migration text; never executable against a real database).
  * `scripts/migrate/fixtures/invalid/**` — negative fixtures (intentionally invalid example text for each failure mode in §13; never executable against a real database).
  * `scripts/migrate/run-validation-tests.mjs` — test harness invoking the validator against the fixtures above.
  Exact final filenames/structure are fixed at Gate C, not by this document.

**Conditionally Allowed — Human Review expansion (not ordinary Allowed Files):**

* Root `package.json`
* Root `package-lock.json`

Neither file is named in the §15 digest's Allowed scope for this task. They are not treated as silently/ordinarily allowed. Their modification is permitted **only if all of the following hold**:

1. Gate B has approved an exact migration-execution tool and exact version (§11.0) that requires a root npm `devDependencies` entry.
2. Gate C has approved the exact `package.json` diff (the new dependency entry and any new `scripts` entries, by exact name) before any file is written.
3. `package-lock.json` changes **only** as the direct, semantic consequence of the Gate-B-approved, Gate-C-diffed dependency addition — no unrelated script, workspace member, dependency, or version may change (verified by semantic diff, per the FND-002 precedent, at Gate E).
4. **If the final Gate B/C tool design does not require a root npm dependency at all** (for example, if the validator alone is sufficient for this task and real migration-execution tooling is deferred to whichever later task first authors an executable migration), then `package.json` and `package-lock.json` remain **Forbidden** — no changes to either file are authorized by this package in that case.

No other paths are proposed as Allowed or Conditionally Allowed. In particular, this draft does **not** propose creating `migrations/platform/**` or `migrations/<domain>/**` subdirectories for real use — those belong to FND-004/FND-005 and are listed under §7 Forbidden Files.

## 7. Forbidden Files

* `migrations/platform/**`, `migrations/<any-domain-schema>/**`, or any migration file containing real application/domain/platform DDL — reserved for FND-004 (schema isolation) and FND-005 (event outbox base).
* `packages/domain/**`, `packages/shared/**`, `packages/infrastructure/**` — other tasks' scope (FND-002 merged; FND-005 onward for infrastructure).
* `apps/**` — FND-001 scope.
* **`.github/workflows/ci.yml` — forbidden without qualification.** This is a settled decision (§3, §5), not an open question: FND-006 owns all CI wiring; FND-003 must not add, remove, or modify any workflow step, job, or comment in this file, including the existing `migration-and-integration-placeholder` job.
* `scripts/dev/**` — FND-000/FND-000.1 scope.
* `docs/adr/**`, `CLAUDE.md`.
* Root `package.json`, root `package-lock.json` — **Forbidden by default**; modification is permitted only under the Conditionally Allowed terms in §6, and only to the exact extent those terms permit. Any change beyond an approved dependency addition and its semantic lockfile consequence is forbidden.
* Any actual database DDL executed against a shared, staging, or production environment. All up/down roundtrip testing in this task must run against an ephemeral, disposable local/CI PostgreSQL instance that is created and torn down within the test run, never a persistent or shared database.
* Any secrets, connection strings with live credentials, or `.env` files containing real values.
* Any business logic, domain model, HTTP route, or queue consumer.
* Any ORM auto-generated schema-sync output (per ADR-000's "禁止 ORM 自動生成 DDL").

## 8. Database and API Changes

No API changes; no `docs/openapi` involvement. No persistent database schema changes of any kind — no `platform` schema, no domain schema, no `event_outbox` table (all reserved for FND-004/FND-005). The only database interaction this task performs is: (a) the up/down roundtrip test applying a framework-only test migration (derived from `migrations/template.sql`'s structure but never the template file itself, which contains no executable DDL — see §12) against a disposable, ephemeral PostgreSQL 16 instance created solely for the duration of the test, then tearing that instance/schema down — mirroring FND-000's ephemeral partition-capability-test methodology (`docs/codex-task-packages/FND-000.md` §7: "拋棄式（ephemeral）測試 schema/table... 於測試流程建立並於結束時 DROP").

## 12. Acceptance Criteria

Distinguished by category, per instruction, so each can be independently reviewed and independently fail without masking the others.

**Framework behavior:**
* `migrations/README.md` and `migrations/template.sql` exist and are internally consistent with each other and with the validator's actual enforced rules.
* `migrations/template.sql` contains no executable DDL — verified by static inspection: no `CREATE TABLE`, `ALTER TABLE`, `CREATE SCHEMA`, `CREATE INDEX`, or `DROP` statement, and no domain/platform object name, appears anywhere in the file.
* If Gate B/C confirm a root-dependency tool is required: that tool can apply a framework-only test migration (structurally derived from, but not identical to, the non-executable template) up and down (or up + forward-fix, per policy) against an ephemeral local/CI PostgreSQL 16 instance with no manual intervention.
* No application, domain, or platform schema object is created by this task (`git status --short`/`git diff --name-status` against `migrations/platform/**`, `migrations/<domain>/**` remain empty).

**Validation behavior:**
* The validator correctly accepts a well-formed migration fixture (exit 0).
* The validator correctly rejects each of the negative fixtures in §13 with a nonzero exit code and a diagnostic identifying the specific rule violated (not a generic failure message).
* The validator distinguishes "0 violations found" from "the validator itself failed to run" — a parser crash, missing config, or command-execution failure must never be reported as a pass.

**Documentation behavior:**
* `migrations/README.md` explicitly documents: directory/naming convention, `owning_context` header format, deterministic-ordering rule, immutability-of-applied-migrations rule, forward-fix policy for shared environments, and the rollback-documentation requirement.
* `migrations/template.sql` matches the documented convention exactly (no drift between README prose and the template's actual structure), while remaining free of executable DDL.

**Local command behavior:**
* The `scripts/migrate/**` developer command(s) run successfully from a clean checkout with only `npm ci` having been run.
* Commands exit nonzero on any validation failure and print which fixture/rule failed.
* The exact local validation command name (fixed at Gate C) is documented as the command a future FND-006 CI step would invoke — this task defines the command but does not invoke it from any CI configuration.

**Scope protection (includes explicit conditional-scope verification, per §6/§7):**
* `git diff --name-status` against `.github/workflows/ci.yml`, `apps/**`, `packages/domain/**`, `packages/shared/**`, `packages/infrastructure/**`, `scripts/dev/**`, `docs/adr/**`, `CLAUDE.md` is empty — with `.github/workflows/ci.yml` specifically confirmed untouched as a settled requirement, not a residual check.
* No separate top-level migration-fixtures test directory exists anywhere in the diff — all fixtures and harnesses are confirmed to live only under `scripts/migrate/**`.

* No real application/domain/platform DDL exists anywhere in the diff introduced by this task.

**Failure-mode behavior:**
