# ADR-000.1：JavaScript Package Manager, Workspace, and Runtime Pinning

| 項目 | 內容 |
| :---- | :---- |
| 狀態 | **Accepted** |
| 來源 | FND-001（Repository bootstrap）planning 階段發現：ADR-000 未指定套件管理器、workspace 策略、或 Node.js 確切版本。本文件依 ADR-000 §2.1「任何棧內替換...需開 ADR-000.x」補充決策紀錄。 |
| 適用範圍 | 5min Coffee Platform 2.0 monorepo 之 JavaScript/TypeScript 套件管理、workspace 結構、Node.js runtime 版本釘定，始於 FND-001；`scripts/dev/`（FND-000 既有工具鏈）之例外地位一併裁定。 |
| 決策者 | Tech Lead |
| 本文件目的 | 補齊 ADR-000 未涵蓋之三項決策（套件管理器、workspace lockfile 策略、Node.js 確切版本），作為 FND-001 root workspace 設定與 FND-000.1（devcontainer/CI Node 版本對齊）之依據與 sign-off evidence。 |

## 背景

`docs/adr/ADR-000.md` 決策項表格涵蓋語言/Runtime（僅寫「Node.js LTS」，未釘定確切版本）、後端框架、資料庫、Migration 工具、ORM/Data Access、Queue、前端框架、部署基線，共 8 項，但未提及：(a) 套件管理器或 monorepo 工具、(b) workspace lockfile 策略、(c) Node.js 確切 major 版本。這三項決策不能由 task 層自行默默選定，需依 ADR-000 §2.1 的棧內變更規則另開 ADR-000.x，一次裁定。

FND-001 planning 階段查證：本機開發環境未安裝 `corepack`、`pnpm`、`yarn` 中任何一者，僅有 Node 內建的 `npm`（11.9.0）可直接使用；`node -v` 於查證當下為 v25.6.1。Node 25 已於 2026-03-31 到達 EOL；v25.6.1 不符合 ADR-000「Node.js LTS」之要求。

## 決策

### 1. Runtime（Node.js 版本）

| 項目 | 決定 |
| :---- | :---- |
| Node.js 版本 | **24 LTS** |
| 專案支援範圍 | `>=24 <25` |
| Node 25 | 不支援；視為 EOL（不在本專案支援範圍內，不得作為開發或 CI 執行環境） |
| `.nvmrc` | 內容為 `24` |

### 2. Package Management（套件管理）

| 項目 | 決定 |
| :---- | :---- |
| 套件管理器 | **npm workspaces**（Node.js/npm 內建功能，不引入獨立套件管理器） |
| Lockfile 策略 | **單一 root `package-lock.json`**，涵蓋整個 monorepo workspace；`apps/**`、`packages/**` 下**不得**存在各自的 workspace-level lockfile |
| 可重現安裝指令 | `npm ci`（讀取 root `package-lock.json`，為 monorepo workspace 之標準可重現安裝方式） |
| `packageManager` 欄位 | root `package.json` 之 `packageManager` 欄位必須包含**單一確切 npm 版本字串**（例如 `npm@11.9.0` 格式），不得使用 `latest` 或任何版本範圍（range）。該確切版本須於 FND-001 dependency review 中另行核准，並須驗證與 Node.js 24 LTS 相容；不得僅因「本機剛好已安裝該版本」而選定。本 ADR 暫不填入最終版本號，待該版本號通過獨立的 Human Review 後始得填入。 |

### 3. `scripts/dev/` 既有例外（FND-000 工具鏈）

* `scripts/dev/` 是 FND-000 建立的**獨立、非 workspace 成員**工具鏈（環境檢查腳本：`smoke-test.mjs`、`partition-test.mjs`），擁有自己的 `package.json` 與已 commit 的 `package-lock.json`。
* `scripts/dev/package-lock.json` **刻意保留**，不因本 ADR 的「單一 root lockfile」政策而移除或合併。
* `scripts/dev/` **不屬於** root npm workspace（root `package.json` 的 `workspaces` 欄位不包含 `scripts/dev`）。
* 本條款**不得**被解讀為違反第 2 項「`apps/**`、`packages/**` 下不得有各自 lockfile」的規則 —— 該規則的適用範圍明確限定於 monorepo workspace 路徑（`apps/**`、`packages/**`），不涵蓋 `scripts/dev/` 這類獨立工具鏈。
* 未來若要將 `scripts/dev/` 併入 root workspace，須另立獨立、已核准的 task，並經 Human Review，不得於其他任務中順帶執行。

### 4. Enforcement（版本強制機制）

| 機制 | 說明 |
| :---- | :---- |
| root `package.json` `engines.node` | 宣告 `"node": ">=24 <25"`（或等效精確語法），標示相容版本範圍。 |
| root `.npmrc` `engine-strict=true` | 使 `engines` 欄位從「安裝時警告」變成「安裝時強制失敗」，涵蓋 root workspace 下所有 `npm install`/`npm ci` 呼叫。 |
| CI / Dev Container | 透過 **FND-000.1**（獨立 patch task）使 `.github/workflows/ci.yml`（`node-version-file: '.nvmrc'`）與 `.devcontainer/Dockerfile`（`node:24-bookworm`）與本 ADR 訂定的 `.nvmrc` 保持一致；此為本 ADR 決策之**結果（consequence）**，非本 ADR 自行修改該兩檔案 —— 檔案層級變更之 Allowed Files 邊界仍以 FND-000.1 task package 為準。 |
| Corepack | **明確不採用** Corepack 作為版本強制機制。Corepack 為選用（optional）工具，非本架構之必要元件；本 ADR 之強制機制完全依賴 `engines` + `engine-strict=true` + `.nvmrc`（由開發者/CI 手動或透過 `nvm use`/`actions/setup-node` 讀取），不假設或要求 Corepack 存在。 |

### 5. Workspace Policy（依賴宣告政策）

* 所有直接依賴（direct dependency）必須宣告在實際使用它的 workspace 成員（`apps/*` 或 `packages/shared/*`）自己的 `package.json` 內，不得僅依賴 root 或其他 workspace 成員的依賴透過 npm hoisting 隱性可用。
* 禁止 import 未宣告的 transitive 或 hoisted 依賴（即使 npm 的 hoisting 行為使其技術上可被 require/import，也視為違規）。
* CI 必須從 root lockfile 執行乾淨安裝（`npm ci`）以驗證 lockfile 與宣告的依賴一致。
* Dependency-boundary linting/validation（例如偵測未宣告依賴的靜態掃描）可於未來任務中在 GA-013（ADR-000 Dependency Allowlist）框架下新增；本 ADR 不要求立即實作該 lint 工具，僅訂定政策本身。

## 理由（Rationale）

**不以「本機剛好已安裝」作為主要理由。** 決策依據如下：

1. **標準 Node 發行工具鏈** — npm 隨 Node.js 官方發行版內建，是 Node 生態系的標準套件管理工具，非特定機器的偶然狀態。
2. **足夠的 workspace 能力** — npm workspaces 已能滿足 FND-001 所需的 monorepo 結構（`apps/*` + `packages/shared/*`），不需要額外的 workspace 編排功能。
3. **降低 onboarding 與 CI 複雜度** — 開發者與 CI 環境只需標準 Node 發行版即可運作，不需額外安裝、設定或版本管理獨立的套件管理器工具。
4. **Root lockfile 可重現性** — 單一 root `package-lock.json` + `npm ci` 提供明確、可稽核、可重現的安裝結果，符合 ADR-000「先求可重現環境」的一貫原則。
5. **現階段 repo 規模不需要額外編排工具** — Phase 1 規模（5-50 QPS，模組化單體，四個 app + 六個 shared package）未達到需要 Lerna/Turborepo/Nx 這類建置編排/快取工具的複雜度門檻。

## 被否決替代方案

| 方案 | 被否決理由 |
| :---- | :---- |
| **pnpm** | 承認其在 phantom-dependency 防護上具有實質優勢（嚴格的 node_modules 結構，禁止未宣告依賴被意外 resolve 成功，防護力優於 npm 的 hoisting 模型）。但現階段裁定不採用：npm workspaces 已足夠覆蓋 FND-001 的需求，且採用 pnpm 需要引入另一個「必要」套件管理器工具（需額外安裝，未經 ADR-000 核准）。若未來 phantom-dependency 事故或依賴隔離需求成為實際痛點，應另開 ADR-000.x 提案重新評估，而非在 task 層自行切換。 |
| **yarn** | 未經 ADR-000 核准；Yarn Classic 與 Yarn Berry 版本分裂會增加設定複雜度與文件維護成本；不採用。 |
| **Lerna** | 現階段 repo 規模（Phase 1 模組化單體）不需要獨立的 monorepo 版本/發布編排工具；npm workspaces 已足夠；不採用。 |
| **Turborepo** | 同上，現階段不需要額外的 build 快取/任務編排層；不採用。 |
| **Nx** | 同上，且 Nx 的專案圖與 generator 生態系對現階段規模而言是過度工程；不採用。 |

## 生效條件

* 本文件簽核為 **Accepted** 前，FND-001 的 root `package.json`（workspaces 設定、`packageManager`、`engines`）、root `.npmrc`、root `package-lock.json` 均不得 commit。
* FND-000.1（devcontainer/CI 之 Node 版本對齊）為本 ADR 決策之結果，其 `node-version-file: '.nvmrc'` 步驟相依於本 ADR 訂定的 `.nvmrc` 內容（`24`）；FND-000.1 不得早於本 ADR 簽核與 FND-001 的 `.nvmrc` 落地而 commit。
* `scripts/dev/package-lock.json` 維持獨立、非 workspace lockfile 之地位，不受本 ADR 影響。`scripts/dev/package.json` 僅可由 **FND-000.1** 修改，且僅限新增 Node 24 `engines` 對齊欄位；此變更**不**使 `scripts/dev` 成為 root workspace 成員，亦**不**授權任何依賴或 lockfile 遷移（見第 3 項）。
